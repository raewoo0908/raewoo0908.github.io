매주 월요일 routine 이 `claude/bilingual-check-<날짜>` 브랜치에 리포트를 올린다. 그걸 받아
고치고 배포하기까지의 전 과정이다. **절차가 길다는 게 어려운 게 아니다** — 판단이 필요한
지점이 몇 군데 숨어 있고, 모르면 조용히 틀린다. 아래 순서와 경고는 그래서 있다.

`$ARGUMENTS` 를 해석한다. 첫 비플래그 인자가 브랜치명, `--except` 뒤의 값들이 손대지 말
글 폴더다. `--except` 값은 `src/content/` 접두를 생략할 수 있다(`pages/cv` = `src/content/pages/cv`).

바꾸면 안 되는 순서가 셋이다.

- **1번의 머지 방향은 main → 브랜치.** 반대로 하면 검증 안 된 내용이 main 에 섞인다.
- **3번이 4번보다 먼저.** 검증 전에 고치기 시작하면 리포트의 오진을 글에 심는다.
- **5번이 6번보다 먼저.** 구조 위반이 있으면 의미 검사가 아예 안 돈다.

## 1. 작업 워크트리 확보

브랜치를 안 줬으면 `git ls-remote --heads origin 'refs/heads/claude/*'` 로 최신 것을 골라
**사용자 확인을 받는다.**

```bash
git fetch origin
git worktree add .claude/worktrees/<브랜치 마지막 세그먼트> <브랜치>
cd .claude/worktrees/<브랜치 마지막 세그먼트>
git merge main
```

- **원본 저장소(`~/GithubBlog`)는 `main` 에 그대로 둔다.** 사용자의 dev 서버도 편집 중인
  파일도 건드리면 안 된다. 이후 7번까지 모든 작업은 워크트리 안에서 한다.
- `git merge main` 은 워크트리 안에서 된다. 머지는 main 을 체크아웃하지 않고 그 커밋만 읽는다.
  routine 이 브랜치를 올린 뒤 사람이 main 에 커밋했을 수 있어 브랜치는 대개 뒤처져 있다.
- **`npm install` 은 하지 않는다.** 검사 스크립트는 전부 node 빌트인만 쓴다. 수정·drift·커밋이
  전부 설치 없이 된다(렌더 확인이 필요할 때만 예외 — 맨 아래).
- `.claude/worktrees/` 는 `.git/info/exclude` 에 있어 추적되지 않는다.

## 2. 리포트 파악

브랜치의 `docs/reports/bilingual-check-*.md` 를 읽어 **글 폴더별로** 항목을 쪼갠다.
`--except` 로 제외된 폴더는 여기서 뺀다.

리포트가 없거나 지적이 0건이면 그 사실만 알리고 끝낸다. **브랜치를 억지로 main 에 병합하지
않는다.**

## 3. 사실 재검증 — 고치기 전에 반드시

리포트의 **사실 지적만** 확인한다. 표현·오타 항목은 대상이 아니다.

- 공식 문서는 WebFetch 로 **원문을 읽는다.** 리포트의 요약을 믿지 않는다.
- 실행으로 확인되는 것은 실행한다. `IMPORT_MODULE` 지적은
  `python3 -c "import dis; dis.dis(compile('from math import *','<s>','exec'))"` 한 줄로
  실제 opcode 가 `IMPORT_NAME` 임이 드러났다.
- **리포트의 전제 자체를 의심한다.** `pages/home` 의 "slide toggle" 지적은 `LangToggle.astro`
  를 읽어보니 실제로 슬라이딩 토글이라 전제가 틀렸다.

> **"문서에서 확인 불가"는 오류의 근거가 아니다.** 부재의 증거일 뿐이다. 2026-08-03 에 이
> 이유로 셋을 걸렀다 — `payload.stop_hook_active`(문서에 안 실렸을 뿐 실재하는 필드),
> `disableAllHooks` 가 statusline 도 끈다는 서술(현행 문서에 그런 말이 없어 리포트 쪽이 틀렸다),
> GitHub 트리거 예시의 "테스트"(문서 예시가 "style" 일 뿐 오류가 아니다).

## 체크포인트 ① — 승인 없이 4번으로 가지 않는다

표로 제시하고 사용자 승인을 받는다.

- 리포트 사실 지적 N 건 중 **검증을 통과한 M 건** — 각각 무엇으로 확인했는지
- **탈락한 건과 그 이유** — 왜 고치지 않는지가 왜 고치는지만큼 중요하다
- 글별 수정 계획과 배정할 모델

## 4. 수정 — 글마다 서브에이전트 (병렬)

글 폴더가 서로 겹치지 않으므로 병렬로 돌려도 충돌하지 않는다. 글 수와 무관하게 **항상**
서브에이전트를 쓴다(동작을 예측 가능하게 유지). SVG 편집·문단 재작성처럼 손이 많이 가면
Opus, 오타·표기 위주면 Sonnet.

각 에이전트에게 **그 글의 리포트 발췌 + 3번에서 살아남은 사실 + 아래 제약**을 준다.

- 담당 폴더 밖 금지 — 다른 에이전트가 동시에 돌고 있다
- 미커밋 WIP 폴더는 열지도 말 것
- **`ko` 가 SSOT. ko 는 오타·비문·명시된 사실 수정만. 그 이상 고치고 싶으면 고치지 말고 보고할 것**
- ko 내용이 바뀌면 en 에도 반영할 것
- 헤딩 개수·표 행/열·코드블록·이미지 참조 수를 ko/en 일치시킬 것
- 이미지 언어쌍 규칙: `ko.md` 는 `.ko.`, `en.md` 는 `.en.`
- **줄 번호를 믿지 말고 문자열로 찾을 것** — 앞선 수정으로 밀린다
- 헤딩을 바꾸면 앵커가 바뀌므로 **그 헤딩으로 오는 링크를 먼저 확인**할 것
- SVG 에 항목이 늘면 좌표를 재배치하고 ko/en 기하를 동일하게 유지할 것
- 커밋·브랜치 변경 금지. 유료 `npm run drift` 금지
- 보고는 항목별 `[고침] / [안 고침 — 이유]`

> ko 수정 범위를 못박는 이유: 2026-08-03 에 한 에이전트가 ko 인용문 문체를 `있다.` →
> `있습니다.` 로 바꿨다. 나쁜 판단은 아니었지만 지시 범위 밖이었고, 사용자가 나중에 발견했다.

## 5. 구조 정렬 — 6번보다 먼저

```bash
node scripts/drift-blocks.mjs <폴더1> <폴더2> … --vs-head
```

**구조 위반이 있으면 `check-drift` 가 LLM 을 아예 안 부른다.** 안 고치고 6번에 가면 통과한
것처럼 보이다가, 나중에 구조가 풀리는 순간 첫 판정이 쏟아진다. 2026-08-03 에 그래서 커밋이
두 번 막혔다.

- `--vs-head` 로 **"내가 깨뜨렸나, 원래 그랬나"** 를 먼저 가린다. `[HEAD]` 도 어긋나 있으면
  회귀가 아니라 원래 있던 것이다.
- 대개는 **ko 가 빈 줄을 빠뜨려 두 블록이 붙은 것**이다. 빈 줄을 넣어도 렌더 결과는 안 바뀐다 —
  CommonMark 에서 리스트·인용은 문단을 끊고 들어간다.
- `drift-blocks` 는 정렬과 코드블록 줄 수를 **함께** 찍는다. `compareStructure` 는 앞 검사에서
  막히면 뒤까지 못 가므로, 정렬만 고치고 넘어가면 줄 수 차이가 나중에 따로 튀어나온다.
- 목차 앵커 불일치는 성격이 다르다. 앵커는 헤딩 텍스트에서 나오므로 한/영이 다를 수밖에 없고
  **고칠 수 있는 게 아니다.** 마커로 면제하되 **ko·en 양쪽에 다 넣는다** — 한쪽만 빼면 반대쪽
  링크가 홀로 남아 어차피 걸린다.

  ```markdown
  <!-- i18n-intentional(links): 목차 앵커는 헤딩 텍스트에서 나오므로 한/영이 다를 수밖에 없습니다 -->
  ```

  범위는 `links`·`images` 뿐이고, 이름을 틀리면 조용히 무시되지 않고 막는다.

## 6. drift 수렴

폴더마다 게이트가 열릴 때까지 돌린다.

```bash
node scripts/check-drift.mjs --dir <폴더>
```

> **`--worktree` 를 쓰지 않는다.** 이 모드는 설계상 `git ls-files --others --exclude-standard`
> 로 **미커밋 초안까지** 훑는다. 2026-08-03 에 사용자의 미완성 글 3개가 딸려 들어가 돈이 샜다.
> `--dir` 은 캐시 적중을 건너뛰고 항상 재판정하며, 통과 기록도 정상적으로 남긴다.

- 라운드마다 **새 건이 나오는 것이 정상이다.** 판정이 틀려서가 아니라, en 을 고치면 그 자체가
  새로운 비교 대상이 되기 때문이다.
- 호출 1회 약 **$0.5**. 누적 비용을 라운드마다 보고한다.
- `DRIFT_MAX_ROUNDS`(기본 3) 상한에 닿으면 스크립트가 유예로 전환해 통과시키고 **그대로
  배포된다.** 거기 닿기 전에 남은 건을 체크포인트 ② 로 올린다.
- 출력에서 **`의미 검사를 건너뜁니다` 를 명시적으로 찾는다.** `claude` CLI 부재·네트워크 실패
  시의 fail-open 은 통과처럼 보이지만 **검증된 것이 아니라 건너뛴 것**이다. 뭉뚱그리면 안 된다.

작업 워크트리는 drift 캐시가 원본 저장소와 갈린다(`git rev-parse --absolute-git-dir` 가
`.git/worktrees/<이름>` 을 준다). 처음부터 판정하니 비용이 조금 더 들지만, 판정 대상이 그
워크트리의 바이트 쌍이므로 남의 기록을 잘못 재사용할 위험은 없다. `pre-commit` 도 정상 동작한다.

## 체크포인트 ②

- `git diff --stat` 와 카테고리별 수정 요약
- **리포트 밖 발견 목록** — 고친 것과 못 고친 것을 나눠서
- 누적 비용
- **미결 항목** — 유예로 넘어간 건, fail-open 으로 검사를 건너뛴 폴더
- 되돌리기 어려운 것(URL 변경 등)은 여기서 따로 묻는다

## 7. 커밋·병합·배포

**작업 워크트리에서**

1. 스테이징은 **리포트가 짚은 폴더만 명시적으로.** `git add src/content` 는 미커밋 초안까지
   쓸어담는다 — 2026-08-03 에 실제로 그랬다.
2. 커밋. 메시지는 카테고리별로 무엇을 왜 고쳤는지 적고, 유예로 남은 건이 있으면 함께 남긴다.
3. `git push origin <브랜치>`

**원본 저장소에서** — 워크트리에서는 main 을 체크아웃할 수 없다(git 이 같은 브랜치를 두
워크트리에 두는 것을 막는다). 그래서 병합만 넘긴다. `--ff-only` 는 새 커밋을 만들지 않아
pre-commit 이 돌지 않고, 원본 저장소는 내내 `main` 에 머문다.

```bash
git fetch origin
git merge --ff-only <브랜치>
git push origin main
gh run watch
```

**라이브 점검**(`https://raewoo0908.github.io/`) 은 새 내용이 있는지와 **옛 내용이 사라졌는지를
둘 다** 본다. SVG 는 해시 URL 을 따라가 파일 안까지 확인한다.

> `draft: true` 인 글이 프로덕션에서 404 인 것은 정상이다. dev 서버에서는 보이므로 배포
> 실패로 오해하기 쉽다.

**워크트리 정리** — 성공해서 사용자가 승인하면 `git worktree remove`. 체크포인트에서
거부했거나 실패로 멈췄으면 **남긴다.** 사람이 그 디렉터리에서 이어받을 수 있어야 한다.

## 막혔을 때

- **3번에서 사실 지적이 전부 탈락** — 정상이다. 표현·오타·drift 항목은 남아 있으므로 4번으로
  간다. "고칠 게 없다"고 끝내면 안 된다.
- **체크포인트에서 거부** — 수정을 작업 트리에 그대로 두고 멈춘다. 되돌리지 않는다.
- **`merge --ff-only` 실패** — 작업하는 사이 누가 main 에 커밋했다. **강제로 밀지 않는다.**
  1번으로 돌아가 main 을 브랜치로 다시 당기고, 6번을 다시 통과시킨 뒤 재시도한다.
- **pre-commit 이 커밋을 막을 때** — 정상 동작이다. 리포트를 읽고 고쳐 재시도한다.
  `SKIP_DRIFT=1` 이나 `--no-verify` 는 **사용자가 명시적으로 지시할 때만** 쓴다.
- **글 폴더를 rename 했을 때** — 셋이 따라온다. ① 그 경로로 오는 인바운드 링크를 전부 갱신,
  ② 공개 URL 이 바뀌므로 체크포인트에서 먼저 승인, ③ drift 캐시(`.git/ko-en-drift-cache.json`)
  에 옛 경로 항목이 고아로 남으므로 지운다 — 폴더가 없어 아무도 읽지 않지만, 남은 `attempts`
  카운터가 나중에 유예를 앞당긴다.
- **렌더 확인이 필요할 때** — SVG 좌표를 고친 경우처럼 눈으로 봐야 하면 그때만 작업 워크트리에서
  `npm install` 후 **`npm run dev -- 4322`** 로 띄운다. **4321 은 쓰지 않는다** — 사용자의
  서버다. `dev.sh` 의 프로세스 정리는 경로를 매칭하므로 원본 저장소의 서버를 죽이지는 않지만,
  포트가 겹치면 누가 잡고 있는지 알리며 멈춘다. 끝나면 `npm run dev:stop`.
  **`npm run build` 는 쓰지 않는다** — dev 서버가 뜬 채로 돌리면 콘텐츠 스토어를 동시에 써서
  본문이 빈 페이지가 조용히 만들어질 수 있다.
