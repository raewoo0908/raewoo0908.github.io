## 1. 글의 뼈대

1. **도입 — `## 0. 들어가며`** (또는 곧바로 `## 1. ~가 등장한 배경`).
   - 상황이나 질문으로 연다. "모델이 내놓은 예측결과를 어떻게 판단할 수 있을까요?"
   - 이전 글과 이어지면 첫 문단에서 **이전 글 내용을 한두 문장으로 되짚고 링크**한 뒤, "그렇다면 ~에서는 어떨까요?"로 이번 글의 문제를 던진다.
   - 특정 글·강의를 기초로 썼다면 도입에 `> 📌 **NOTE**`로 출처를 밝힌다.
2. **요약은 앞에 둔다.** 내용이 많은 글은 도입 직후 `> 📌 **총정리**`(번호 목록), 절 첫머리에는 `> 📌 **한 줄 요약**` · `**핵심 아이디어**`를 놓는다. 끝에 따로 "요약" 절을 만들지 않는다.
3. **본문 — 유형별 서사**(13절 템플릿). 공통 원리는 **"문제 → 해결 → 그 해결의 한계 → 다음 해결"**.
4. **마무리** — 유형에 따라 셋 중 하나.
   - 개념글: 마지막 개념의 결론 문장으로 닫는다. "그래서 이제 특정 모델의 모든 threshold에 대한 예측 성능을 하나의 수치 AUROC로 나타낼 수 있게 되었습니다!"
   - 실전 코드 절(`## N. 코드로 활용하는 법`, `## N. 그래서 코드는 어떻게 씀?`)로 끝낸다.
   - 실험글: 결론 절에서 **도입의 질문을 다시 인용하고 하나씩 답**한 뒤, `> ☺️` 다음 포스트 예고.
5. **`## 📚 참고자료` — 필수**(14절).

## 2. 헤딩

- **번호로 구조를 드러낸다**: `## 1.` → `### 1.1.` → `#### 1.1.1.` (끝 점 포함). `3-1.` 같은 하이픈 표기는 쓰지 않는다.
- **본문에 `#`(H1)을 쓰지 않는다.** 페이지 제목이 H1이다.
- **목차는 자동 생성되고 H2·H3만 모은다**(`src/lib/toc.ts`). H4는 목차에 안 나오니, 목차에서 보여야 할 단위는 H3까지로 끊는다. 본문에 목차를 손으로 쓰지 않는다.
- **헤딩 문구는 그 절의 질문이거나 결론이다.** 명사 나열보다 이쪽이 이 블로그의 결이다.
  - 질문: `## 3. 객체 탐지에서 AU-ROC를 사용할 수 없을까?` · `### 3.2. Fast R-CNN이 R-CNN의 한계들을 정리했나?`
  - 결론: `### 발견 1: 데이터 증강은 과적합 방지에 도움이 될 수 있지만, 모델 예측 정확도를 보장하지는 않는다!`
  - 구어: `## 5. 그래서 코드는 어떻게 씀?`
  - 한계 고발: `#### 2.2.1. Selective Search의 한계: CPU에서 직렬로 이루어진다.`
- **헤딩에 이모지는 기본으로 붙이지 않는다.** 예외는 `## 📚 참고자료`, 그리고 한 개념 안의 소단계를 가볍게 구분할 때다(`### 🕵️‍♂️ Prediction` / `### ✏️ Training`).

### 글 제목 · 커스텀 이미지 이모지 (`:이름:`)

**글 제목(frontmatter `title`)은 카테고리 이모지로 시작한다** — 목록에서 시리즈가 한눈에 묶여 보이게.

- `posts/ai/` → `:ai:`
- `posts/ai/practical-statistics-for-data-scientists/` → `:psds:` (상위 `:ai:` 대신)
- `posts/claude/` → `:claude:`
- `posts/python/` → `:python:`

유니코드 이모지로 부족할 때(로고·서비스 아이콘·캐릭터 등) 이미지를 이모지처럼 쓸 수 있다. 본문에서도 `:github:` `:kaggle:`처럼 링크 앞에 붙여 쓴다.

1. 이미지를 **`src/assets/emoji/<이름>.<확장자>`** 에 둔다. 크기는 신경 쓰지 않아도 된다 — 다운받은 원본을 그대로 넣으면 빌드가 알아서 줄이고 webp로 바꾼다.
2. 본문·헤딩·**글 제목(frontmatter `title`)·설명** 어디서든 `:이름:` 으로 부른다.

```markdown
---
title: ':astro: Astro로 블로그 만들기'
description: ':astro: 정적 사이트 생성기로 한/영 블로그를 만든 기록'
---

## 1. :astro: 왜 Astro인가

Astro는 :zero-js: 기본값으로 JS를 보내지 않는다.
```

> ⚠️ **frontmatter에서는 값 전체를 반드시 따옴표로 감쌀 것.** `title`·`description`은 YAML이라, 값이 `:` 로 시작하면 YAML이 그걸 매핑 구분자로 오해해 `bad indentation of a mapping entry` 로 빌드가 죽는다. 본문에서는 따옴표가 필요 없다.
>
> ```yaml
> description: :claude: 훅을 설정하는 법   # ✗ YAML 파싱 에러
> description: ":claude: 훅을 설정하는 법"  # ✓
> ```

- **이름 규칙**: 영소문자로 시작, 2자 이상, `a-z 0-9 _ -`. 파일명이 곧 이름이다.
- **확장자**: `.png .jpg .jpeg .webp .svg`. **`.gif`는 막아 두었다** — 리사이즈하면 애니메이션이 첫 프레임만 남아 조용히 깨지기 때문.
- **크기는 항상 글자 높이(1em)** 에 맞춰진다. 제목에 쓰면 제목 크기로, 본문에 쓰면 본문 크기로 자동으로 따라간다.
- **목차·글 목록 카드에도 그대로 나온다.** 브라우저 탭 제목처럼 이미지를 넣을 수 없는 자리에서는 토큰이 자동으로 제거된다.
- **오타는 빌드가 막는다.** 등록되지 않은 이름을 쓰면 빌드가 실패하며 비슷한 이름을 알려준다.
- **콜론 표기를 그대로 보여주고 싶으면** 인라인 코드로 감싼다: `` `:sample:` ``. 코드블록 안도 건드리지 않는다. `10:30:00`, `3:2:1` 같은 자연스러운 콜론 표현도 안전하다.
- dev 서버를 켠 채로 새 이모지 파일을 추가했다면 **서버를 다시 시작**해야 인식된다.

## 3. 강조

- **`<u>**밑줄 굵게**</u>` — 이 블로그의 시그니처.** 정의 문장, 결론 문장, "이 문단에서 하나만 기억한다면" 하는 구절에 쓴다. 문단마다 1~3개.
  - 정의: "이 점수를 <u>**정확도**</u>라고 하며, <u>**전체 예측 개수 중에서 올바르게 예측한 샘플의 비율**</u>을 의미합니다."
  - 결론 한 방: 실험 발견의 마지막 문단은 통째로 감싼다. "<u>**즉, 데이터 증강은 과적합을 막아주고 있습니다. 하지만 …**</u>"
  - 감탄·전환: `<u><strong><em>백문이 불여일견!</em></strong></u>`, `<u><strong>하.지.만. validation은 달랐습니다.</strong></u>`
- **`**굵게**`** — 용어의 첫 등장, 리스트 항목의 제목, `**분석 결과**` 같은 라벨.
- **`⭐️ →`** 그 절의 핵심 한 줄, **`→`** 귀결·결과를 잇는 화살표.

> 💡 **굵게가 안 먹는 경우 — `<strong>`으로 쓴다.**
>
> 마크다운은 `**` 안쪽 끝이 문장부호(`)` `.` `"` …)이고 바깥에 한글이 바로 붙으면 굵게로 인식하지 못한다. `**선형 분리 가능(Linearly Separable)**하다`는 별표가 그대로 보인다. 이럴 때는 `<strong>선형 분리 가능(Linearly Separable)</strong>하다`로 쓴다. `<u>**…**</u>`로 감싸면 바깥이 `<`라 문제없다.

## 5. 설명 방식 — 깊이를 만드는 장치

이 블로그 글의 깊이는 아래 장치에서 나온다. 새 글은 이걸 기본으로 갖춘다.

### 5.1. 질문으로 다음 문단을 연다

절과 절, 문단과 문단 사이를 독자의 의문으로 잇는다. 그리고 바로 답한다.

- "두 로봇 모두 정확도 60%이니, 두 로봇은 같은 성능을 보이는 걸까요?"
- "이제 F1-Score라는 하나의 숫자로 성능을 표현할 수 있게 되었습니다. 그러면 만사 오케이인 걸까요?"
- "객체 탐지에서도 AU-ROC를 쓰면 될 것 같은데, 과연 그럴까요? 답은 <u>**'NO'**</u>입니다."

### 5.2. 한계가 다음 개념을 부른다 (계보 서사)

개념을 나열하지 않고 **"이게 왜 부족했는가"** 로 다음 개념을 등장시킨다. 한계는 말로 끝내지 않고 **수치·수식·그림·코드로 증명**한다.

- 계단함수(오차 획일화·미분 불가) → 시그모이드(기울기 최대 0.25, non-zero centered → 지그재그) → tanh → ReLU(음수 구간 0) → Leaky ReLU 계열
- R-CNN(이미지당 47초, 2000번 중복 conv) → Fast R-CNN(Selective Search 2초가 병목으로 남음) → Faster R-CNN(RPN, 10ms)
- Accuracy(같은 60%) → Precision/Recall → F1(threshold 따라 바뀜) → AU-ROC(TN 무한대라 객체 탐지엔 못 씀) → AP → mAP
- 해결 여부는 표로 정리한다: `| 한계 | 해결 여부(✅/❌) | 그림에서 대응되는 부분 |`

### 5.3. 직관 → 엄밀, 두 단으로 설명한다

같은 개념을 비유로 한 번, 수식·구현으로 한 번 설명한다. 라벨을 붙여 둘을 구분한다.

```markdown
- **비유적 설명**

  우리의 모델(학생)이 … 시스템(선생님)은 학생이 얼마나 잘 했는지 채점해야 합니다.

- **엄밀한 설명**

  $$
  L(\theta \mid X) = P(X \mid \theta)
  $$
```

`- **개념적으로:**` / `- **엄밀하게:**` 도 같은 패턴이다(RPN: "슬라이딩 window처럼 보이지만, 엄밀하게는 3×3 conv 뒤의 1×1 conv 두 개로 구현된다").

### 5.4. 예시 하나를 끝까지 끌고 간다

글 초반에 구체적 상황 하나를 세우고 마지막 개념까지 그 예시로 설명한다. 독자를 그 상황의 당사자로 만든다("우리 회사", "우리 모델", "저희가 만드는 모델").

- 불량 검출 로봇 A·B → 정확도부터 ROC까지
- 혈액 세포 탐지(YOLOv3 vs EfficientDet) → TP/FP 판정부터 mAP까지
- 마법의 동전(그림 0.7) → 베르누이 → 우도

### 5.5. 손으로 계산해 보인다

공식만 쓰지 않고 **작은 예제를 직접 계산**한다. 숫자는 실제로 맞아야 한다(Claude는 반드시 검산한다).

- AND 게이트의 입력 4가지를 하나씩 대입해 `step()` 결과를 확인
- Confidence Threshold를 0.3 → 0.5 → 0.7 → 0.9로 바꿔가며 Precision·Recall을 계산하고 표로 정리
- 같은 PR Curve의 AP를 11-point·all-point·101-point로 각각 계산해 차이를 보여줌

### 5.6. 비유·극단 예시

추상 개념은 일상 장면에 붙인다.

- 계단함수의 오차 획일화 → "0점을 맞은 학생이나 59점을 받은 학생이나 똑같이 F를 주는 성격 더러운 교수님"
- 확률 출력의 의미 → "발사이즈 270은 커 보이지 않지만, 한국 기준 상위 70%라는 걸 알면 의미가 생긴다"
- RoI projection → "쿠키 반죽(feature map)에 쿠키 커터(RoI)"
- Precision·Recall trade-off → "한정된 화살로 네 구역 과녁을 쏘는 양궁"

### 5.7. "왜 하필 그것인가"를 끝까지 판다 ← 가장 중요

상수·경계·설계 선택이 나오면 그 **근거**를 판다. 보통 🤔 콜아웃이 되고, 본문 한 절만큼 길어져도 된다.

- ✗ "AP를 계산할 때 Confidence 하한은 0에 가깝게 둡니다."
- ✓ 위 문장 **+** 하한을 0.75로 올렸을 때 AP가 0.867 → 0.667로 떨어지는 계산 → `🤔 그럼 모든 confidence를 살리면 FP가 늘어 손해 아닌가요?` → 낮은 confidence 예측은 정렬 맨 뒤에 붙어 곡선 앞부분을 안 바꾼다는 표 → 보간 때문에 AP가 줄 수 없다는 논증 → "0으로 두지 않는 건 계산량 때문"이라는 결론까지.

## 6. 수식

- 인라인은 `$…$`, 블록은 `$$…$$`. 여러 줄 유도는 `\begin{aligned}`나 `\\`로 줄을 나눈다.
- **기호는 쓰기 전에 불릿으로 정의**한다: `- $(x_i, y_i)$: $i$번째 데이터의 **입력 피처**와 **정답 라벨**`
- **유도는 한 단계씩, 단계마다 무엇을 했는지 한 줄**로 쓴다.

  ```markdown
  - 양변에 역수를 취합니다.

  $$
  1 + e^{-(w^T x + b)} = 2
  $$

  - 양변에서 1을 뺍니다.
  ```

- 유도 중에 생긴 문제는 라벨로 드러낸다: `- **문제점:** … 언더플로우` → `- **해결법 1: 식 전체에 마이너스를 붙이자!**`
- 유도 끝에는 이름을 붙인다: "이것이 바로 로지스틱 회귀에서 사용하는 손실함수인 <strong>이진 크로스 엔트로피</strong>의 최종 형태입니다."
- **수식 뒤엔 반드시 의미를 말로 푼다.** "즉, 시그모이드는 … 찌그러뜨리는 역할만 할 뿐, 기준선 자체는 선형 방정식이 결정합니다."
- 경우 나누기는 번호 목록 + 각 항목 안의 수식 + `→ 0 AND 0 = 0`식 결론으로 쓴다.

- **개념글에도 코드를 쓴다.** 두 가지 자리가 있다.

  - ✓ `>>> sys.getsizeof(3.14)` 다음 줄에 `24    # 16(헤더) + 8(double)`

## 13. 글 유형별 템플릿

### A. 개념 계보형 (예: 활성화함수, R-CNN 계열, 평가지표)

```
0. 들어가며(이전 글 되짚기 · "그렇다면 ~는?" 질문) → [📌 총정리]
→ 1. 기존 방법과 그 한계(수치·수식·그림·코드로 증명)
→ 2. 해결책의 등장(직관 → 엄밀 → 손계산 예시 → 🤔 Q&A로 "왜?")
→ 3. 그 해결책의 한계 → 4. 다음 해결책 … (반복, 해결 여부 표)
→ (선택) 최신 흐름 한 절
→ N. 코드로 활용하는 법(선택) → 📚 참고자료
```

### B. 실험·EDA 리포트형 (예: 정규화·증강 실험, X-Ray EDA)

```
0/1. 들어가며(어떤 과제·수업에서 · > 🤔 검증할 질문들 · 통념/LLM 답 · "직접 해보자")
→ 사용한 데이터·코드(:kaggle: :github: 콜아웃) · 📌 진행 순서 / 실험 설계 표 · 감수하는 한계
→ 데이터 준비 → 모델·방법 → 실행(핵심 코드 발췌 + 왜 그렇게 짰나 + 💡 구현 함정)
→ 결과(📌 이 실험의 한계 → 전체 그림 → ### 발견 N: <결론 문장> 또는 **분석 결과**·**결론**·**우려사항**)
→ 결론(도입의 🤔 질문을 다시 인용하고 **답** →) → > ☺️ 다음 포스트 예고 → 📚 참고자료
```

- 각 분석 절은 **"왜 확인하는가(목적) → 그림·표 → 분석 결과 → 결론(다음 행동)"** 순서다. 결론은 "그래서 무엇을 하기로 했는가"로 끝난다.

### C. 책·강의 정리형 (예: PSDS 시리즈)

```
절마다: 도입 문단(이전 절·이전 글과 연결) → [> 📌 핵심 요약]
→ | 용어 | 의미 | 비고 | 표 → 개념 + 수식 → 책·강의 그림 + 해석 불릿
→ > 📌 NOTE(헷갈리는 두 개념 비교, 책 밖 보충)
→ 📚 참고자료(원서 노트북·보조 자료)
```

### D. How-to · 도구 글 (예: claude·git 카테고리)

```
0. 들어가며(무엇이 불편했나 · 이걸로 무엇을 해결하나 — 질문으로)
→ 1. 동작 원리(직관 → 엄밀, 다이어그램)
→ 2. 설정 단계(번호 리스트 + 코드블록 + 출력 + 해석)
→ 3. 실전 예시 → 🤔 Q&A로 함정과 "왜 그렇게 동작하나"
→ 📚 참고자료
```

## 14. 글 말미 — 📚 참고자료

- 마지막에 **`## 📚 참고자료`** 를 두고 본문에서 기댄 논문·강의·블로그·영상·내 코드 저장소(`:github:`)를 나열한다.
- 링크 텍스트는 **원 제목 그대로** 쓴다. 한 줄 설명은 선택이다.
- 도입에서 "기초로 삼았다"고 밝힌 글은 여기에도 반드시 넣는다.
- 링크가 죽지 않도록 **URL은 쓰기 전에 실제 존재를 확인**한다.
- Claude Code 공식 문서 도메인은 **`code.claude.com/docs/en/...`** (구 `docs.claude.com`은 301 리다이렉트).
