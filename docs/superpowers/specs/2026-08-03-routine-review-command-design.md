# `/routine-review` — routine 이 올린 이중언어 점검 브랜치를 받아 배포까지

작성일 2026-08-03 · 상태: 설계 승인됨

## 배경

매주 월요일 routine 이 `claude/bilingual-check-<날짜>` 브랜치에 `docs/reports/bilingual-check-<날짜>.md` 를 올린다. 지금은 그 리포트를 사람이 읽고, 브랜치를 받아, 글을 고치고, drift 게이트를 통과시켜 커밋하고, main 에 병합해 배포한 뒤, 라이브에서 확인한다. 2026-08-03 에 이 과정을 한 번 손으로 완주했다. 그때 겪은 것들을 커맨드에 담아 반복 가능하게 만든다.

손으로 해보니 **절차가 길다는 게 문제가 아니었다.** 문제는 판단이 필요한 지점이 몇 군데 숨어 있고, 그걸 모르면 조용히 틀린다는 것이었다.

- 리포트가 짚은 사실 관련 지적을 재검증했더니 **3건이 오진이었다.** 그대로 고쳤으면 멀쩡한 글에 오류를 심을 뻔했다.
- `check-drift.mjs` 는 구조 위반이 있으면 LLM 을 아예 부르지 않는다. 그래서 4개 폴더가 **한 번도 의미 검사를 받은 적 없는 상태**로 통과해 있었고, 구조를 고치는 순간 첫 판정 15건이 쏟아지며 커밋이 두 번 막혔다.
- `check-drift.mjs --worktree` 는 설계상 미커밋 초안까지 훑는다. 사용자의 미완성 글 3개가 딸려 들어가 돈이 샜다.
- `git add src/content` 가 그 미커밋 초안을 스테이징했다.

## 산출물

1. `.claude/commands/routine-review.md` — 슬래시 커맨드 `/routine-review`
2. `scripts/drift-blocks.mjs` — ko/en 블록 정렬 진단 도구
3. `scripts/drift-blocks.test.mjs` — 위 도구의 회귀 테스트

## 용어

git 문서의 main worktree / linked worktree 를 쓰되, `main` **브랜치**와 겹치지 않게 다음 이름으로 부른다.

| 이름 | 실체 | 이 설계에서의 역할 |
| --- | --- | --- |
| **원본 저장소** | `~/GithubBlog` (git 의 main worktree) | 사용자 작업 공간. `main` 브랜치에 내내 머문다. dev 서버가 4321 에서 도는 곳. 마지막 `merge --ff-only` + `push origin main` 만 여기서 한다 |
| **작업 워크트리** | `.claude/worktrees/<브랜치 마지막 세그먼트>` (linked worktree) | 커맨드가 실제로 일하는 곳. 리포트 읽기·수정·drift·커밋·브랜치 push |

## 인터페이스

```
/routine-review [브랜치명] [--except <폴더>...]
```

- 브랜치를 생략하면 `git ls-remote --heads origin 'refs/heads/claude/*'` 로 최신 것을 골라 확인을 받는다.
- `--except` 는 "지금 공사 중이라 건들지 마라"를 넘기는 통로다. 값은 `src/content/` 아래의 글 폴더 경로이며, 앞의 `src/content/` 는 생략할 수 있다(`pages/cv` 와 `src/content/pages/cv` 가 같다). 2026-08-03 에는 CV 가 여기 해당했다.

## 전체 흐름

```
① 워크트리 확보   git worktree add → cd → git merge main
② 리포트 파악     리포트를 글별 항목으로 분해
③ 사실 재검증     리포트의 사실 지적만 공식 문서·실행으로 직접 확인
   ══════ 체크포인트 ① : 검증 결과 + 수정 계획 승인 ══════
④ 수정           글마다 서브에이전트 병렬
⑤ 구조 정렬      drift-blocks.mjs 진단 → 교정
⑥ drift 수렴     check-drift --dir 를 폴더별로, 게이트가 열릴 때까지
   ══════ 체크포인트 ② : diff·비용·미결 승인 ══════
⑦ 커밋·병합·배포  워크트리에서 커밋·push → 원본 저장소에서 ff·push → 라이브 점검
```

세 가지 순서가 설계의 핵심이며 바꾸면 안 된다.

- **머지 방향** — ① 에서 main 을 브랜치로 당긴다. routine 이 브랜치를 올린 뒤 사람이 main 에 커밋했을 수 있어 브랜치가 뒤처진 채 시작한다. 반대로 하면 검증 안 된 내용이 main 에 섞인다.
- **③ 이 ④ 보다 먼저** — 검증 전에 고치기 시작하면 리포트의 오진을 글에 심는다.
- **⑤ 가 ⑥ 보다 먼저** — 구조 위반이 있으면 의미 검사가 돌지 않는다. 구조를 안 고치고 ⑥ 에 가면 통과한 것처럼 보이다가, 나중에 구조가 풀리는 순간 첫 판정이 쏟아진다.

## 단계별 설계

### ① 워크트리 확보

```bash
git fetch origin
git worktree add .claude/worktrees/<브랜치 마지막 세그먼트> <브랜치>
cd .claude/worktrees/<브랜치 마지막 세그먼트>
git merge main
```

- 원본 저장소는 `main` 에 그대로 머문다. 사용자의 dev 서버도 편집 중인 파일도 건드리지 않는다.
- `.git/info/exclude` 에 `**/.claude/worktrees/` 가 이미 있어 추적되지 않는다. 저장소에 이미 `post-worktree-guide` 워크트리가 있으므로 기존 관행을 따르는 것이다.
- **`npm install` 은 하지 않는다.** 검사 스크립트는 전부 node 빌트인만 쓴다 — `node_modules` 를 치우고 `check-bilingual`·`check-post-images`·`node --test scripts/` 를 돌려 확인했다. 수정·drift·커밋이 전부 설치 없이 된다.
- 워크트리 안에서 `git merge main` 은 된다. 머지는 main 을 체크아웃하지 않고 그 커밋만 읽는다.

### ② 리포트 파악

브랜치의 `docs/reports/bilingual-check-*.md` 를 읽어 **글 폴더별로** 항목을 분해한다. `--except` 로 제외된 폴더는 여기서 뺀다.

### ③ 사실 재검증

리포트의 **사실 지적만** 확인한다. 표현·오타 항목은 대상이 아니다.

- 공식 문서는 WebFetch 로 **원문을 읽는다.** 리포트의 요약을 믿지 않는다.
- 실행으로 확인되는 것은 실행한다. `IMPORT_MODULE` 은 `python3 -c "import dis; dis.dis(compile('from math import *','<s>','exec'))"` 한 줄로 실제 opcode 가 `IMPORT_NAME` 임이 드러났다.
- **리포트의 전제 자체를 의심한다.** `pages/home` 의 "slide toggle" 지적은 `LangToggle.astro` 를 읽어보니 실제로 슬라이딩 토글이라 전제가 틀렸다.

> **"문서에서 확인 불가"는 오류의 근거가 아니다.** 부재의 증거일 뿐이다. 2026-08-03 에 이 이유로 셋을 걸렀다 — `payload.stop_hook_active`(문서에 안 실렸을 뿐 실재하는 필드), `disableAllHooks` 가 statusline 도 끈다는 서술(현행 문서에 그런 말이 없어 리포트 쪽이 틀렸다), GitHub 트리거 예시의 "테스트"(문서 예시가 "style" 일 뿐 오류가 아니다).

### 체크포인트 ①

다음을 표로 제시하고 승인을 받는다.

- 리포트 사실 지적 N 건 중 **검증을 통과한 M 건** — 각각 무엇으로 확인했는지
- **탈락한 건과 그 이유** — 왜 고치지 않는지가 왜 고치는지만큼 중요하다
- 글별 수정 계획과 배정할 모델

### ④ 수정 — 글마다 서브에이전트

글 폴더가 서로 겹치지 않으므로 병렬로 돌려도 충돌하지 않는다. 글 수와 무관하게 **항상** 서브에이전트를 쓴다(동작을 예측 가능하게 유지).

모델은 수정량으로 나눈다. SVG 편집·문단 재작성처럼 손이 많이 가면 Opus, 오타·표기 위주면 Sonnet.

각 에이전트에게 **그 글의 리포트 발췌 + ③ 에서 살아남은 사실 + 아래 제약**을 준다.

- 담당 폴더 밖 금지 — 다른 에이전트가 동시에 돌고 있다
- 미커밋 WIP 폴더는 열지도 말 것
- `ko` 가 SSOT. ko 는 **오타·비문·명시된 사실 수정만**. 그 이상 고치고 싶으면 고치지 말고 보고할 것
- ko 내용이 바뀌면 en 에도 반영할 것
- 헤딩 개수·표 행/열·코드블록·이미지 참조 수를 ko/en 일치시킬 것
- 이미지 언어쌍 규칙: `ko.md` 는 `.ko.`, `en.md` 는 `.en.`
- **줄 번호를 믿지 말고 문자열로 찾을 것** — 앞선 수정으로 밀린다
- 헤딩을 바꾸면 앵커가 바뀌므로 **그 헤딩으로 가는 링크를 먼저 확인**할 것
- SVG 에 항목이 늘면 좌표를 재배치하고 ko/en 기하를 동일하게 유지할 것
- 커밋·브랜치 변경 금지. 유료 `npm run drift` 금지
- 보고는 항목별 `[고침] / [안 고침 — 이유]`

> ko 수정 범위를 못박는 이유: 2026-08-03 에 한 에이전트가 ko 인용문 문체를 `있다.` → `있습니다.` 로 바꿨다. 문서 나머지가 합쇼체라 나쁜 판단은 아니었지만 지시 범위 밖이었고, 사용자가 나중에 발견했다.

### ⑤ 구조 정렬

폴더마다 `node scripts/drift-blocks.mjs <폴더>` 를 돌려 진단하고 고친다.

2026-08-03 의 구조 위반 4건은 **전부 ko 가 빈 줄을 빠뜨려 두 블록이 하나로 붙은 것**이었다. 렌더 결과는 바뀌지 않는다 — CommonMark 에서 리스트·인용은 문단을 끊고 들어가므로, 빈 줄을 넣어도 같은 HTML 이 나온다.

앵커 링크 불일치는 성격이 다르다. 목차 앵커는 헤딩 텍스트에서 나오므로 한/영이 다를 수밖에 없고 **고칠 수 있는 게 아니다.** 마커로 면제한다.

```markdown
<!-- i18n-intentional(links): 목차 앵커는 헤딩 텍스트에서 나오므로 한/영이 다를 수밖에 없습니다 -->
```

**마커는 ko·en 양쪽에 다 넣는다.** 한쪽만 빼면 반대쪽 링크가 홀로 남아 어차피 걸린다. 쓸 수 있는 범위는 `links` 와 `images` 뿐이고, 이름을 틀리면 조용히 무시되지 않고 막힌다.

### ⑥ drift 수렴

폴더마다 **`node scripts/check-drift.mjs --dir <폴더>`** 를 게이트가 열릴 때까지 돌린다.

> **`--worktree` 를 쓰지 않는다.** 이 모드는 설계상 `git ls-files --others --exclude-standard` 로 **미커밋 초안까지** 훑는다. `--dir` 은 캐시 적중을 건너뛰고 항상 재판정하며(`mode !== 'dir'` 가드), 통과 기록도 정상적으로 남긴다.

라운드마다 **새 건이 나오는 것이 정상이다.** 판정이 틀려서가 아니라, en 을 고치면 그 자체가 새로운 비교 대상이 되기 때문이다. 누적 비용을 라운드마다 보고한다. `DRIFT_MAX_ROUNDS`(기본 3) 상한에 닿으면 스크립트가 유예로 전환해 통과시키므로, 거기 닿기 전에 남은 건을 체크포인트 ② 로 올린다.

작업 워크트리에서는 drift 캐시가 원본 저장소와 **갈린다**. `git rev-parse --absolute-git-dir` 가 `.git/worktrees/<이름>` 을 돌려주기 때문이다. 원본의 통과 기록이 안 보여 처음부터 판정하니 비용이 조금 더 들지만, 판정 대상이 그 워크트리의 바이트 쌍이므로 남의 기록을 잘못 재사용할 위험은 없다. `pre-commit` 도 `git rev-parse --show-toplevel` 로 워크트리의 스크립트를 부르므로 정상 동작한다.

### 체크포인트 ②

- `git diff --stat` 와 카테고리별 수정 요약
- **리포트 밖 발견 목록** — 고친 것과 못 고친 것을 나눠서
- 누적 비용
- **미결 항목** — 유예로 넘어간 건, fail-open 으로 검사를 건너뛴 폴더
- 되돌리기 어려운 것(URL 변경 등)은 여기서 따로 묻는다

### ⑦ 커밋·병합·배포

**작업 워크트리에서**

1. 스테이징은 **리포트가 짚은 폴더만 명시적으로.** `git add src/content` 는 미커밋 초안까지 쓸어담는다.
2. 커밋. 메시지는 카테고리별로 무엇을 왜 고쳤는지 적고, 유예로 남은 건이 있으면 함께 남긴다.
3. `git push origin <브랜치>`

**원본 저장소에서**

4. `git fetch origin`
5. `git merge --ff-only <브랜치>`
6. `git push origin main`
7. `gh run watch` 로 배포 확인

> 작업 워크트리에서는 main 을 체크아웃할 수 없다. git 이 같은 브랜치를 두 워크트리에 두는 것을 막기 때문이다. 그래서 병합만 원본 저장소로 넘긴다. `--ff-only` 는 새 커밋을 만들지 않아 pre-commit 이 돌지 않고, 원본 저장소는 내내 `main` 에 머문다.

**라이브 점검** 은 새 내용이 있는지와 **옛 내용이 사라졌는지를 둘 다** 본다. SVG 는 해시 URL 을 따라가 파일 안까지 확인한다.

> `draft: true` 인 글이 프로덕션에서 404 인 것은 정상이다. dev 서버에서는 보이므로 배포 실패로 오해하기 쉽다.

**워크트리 정리** — 성공해서 사용자가 승인하면 `git worktree remove`. 체크포인트에서 거부했거나 실패로 멈췄으면 **남긴다.** 사람이 그 디렉터리에서 이어받을 수 있어야 한다.

## `scripts/drift-blocks.mjs`

### 존재 이유

`check-drift.mjs` 는 `블록 수가 다릅니다 — ko 145개 / en 146개` 까지만 알려주고 **어느 블록인지는 말하지 않는다.** 145 개를 눈으로 세는 것은 불가능하다. 그 간극을 메운다.

### 인터페이스

```bash
node scripts/drift-blocks.mjs <글폴더> [--vs-head]
```

`check-drift.mjs` 가 이미 export 하는 `analyze()` 와 `compareStructure()` 를 그대로 쓴다. **판정 로직을 새로 만들지 않는다** — 같은 파서를 써야 진단과 게이트가 어긋나지 않는다.

### 출력

```
src/content/posts/claude/routine   ko 145블록 / en 146블록
  en 에만  para@en:204   That takes some setup. ⏎ - **Install the Claude GitHub App**
  ⚠ 4번째 코드블록  ko:157(29줄) / en:157(30줄)
```

블록 종류 시퀀스를 LCS 로 정렬해 한쪽에만 있는 블록을 줄 번호·발췌와 함께 찍는다. 어긋난 것이 없으면 `정렬 일치`.

**정렬과 코드블록 줄 수를 함께 뽑는 이유** — `compareStructure` 는 앞 검사에서 실패하면 뒤 검사까지 가지 못한다. 2026-08-03 에 정렬을 고치고 다시 돌렸더니 그 뒤에 가려져 있던 코드블록 줄 수 차이 2건이 새로 나왔다. 한 번에 보여주면 왕복이 없다.

### `--vs-head`

HEAD 시점과 현재를 나란히 찍는다. 구조 위반을 마주쳤을 때의 첫 질문은 **"내가 깨뜨렸나, 원래 그랬나"** 이고, 이것으로 즉답이 된다. 2026-08-03 에 `routine` 이 143/144 → 145/146 으로 절대 수는 변했지만 어긋남의 성격은 HEAD 와 동일하다는 것을 이 비교로 확인해 회귀가 아니라고 판단했다.

### 성격

LLM 을 부르지 않으므로 **공짜**다. 게이트가 아니라 진단 도구이므로 **항상 exit 0** 이다 — `check-*` 스크립트들과 혼동하면 안 된다.

### 테스트

`scripts/drift-blocks.test.mjs`. 픽스처 네 가지.

1. ko 가 리스트 앞 빈 줄을 빠뜨린 경우 → `en 에만 list` 가 나온다
2. 완전 일치 → `정렬 일치`
3. 코드블록 줄 수 차이 → 경고 줄이 나온다
4. `.mdx` 짝도 다룬다

## 실패·중단 처리

**리포트가 없거나 지적이 0건** — 그 사실만 알리고 끝낸다. 브랜치를 억지로 main 에 병합하지 않는다.

**③ 에서 사실 지적이 전부 탈락** — 정상이다. 표현·오타·drift 항목은 남아 있으므로 ④ 로 간다. "고칠 게 없다"고 끝내면 안 된다.

**체크포인트에서 거부** — 수정을 작업 트리에 그대로 두고 멈춘다. 되돌리지 않는다. 워크트리도 남긴다.

**`check-drift` 가 fail-open 했을 때** — `claude` CLI 가 없거나 네트워크가 죽으면 이 스크립트는 경고만 남기고 통과시킨다. 커밋을 못 하게 막지 않으려는 의도적 설계지만 출력이 통과처럼 보인다. 커맨드는 `의미 검사를 건너뜁니다` 경고를 **명시적으로 찾아** 체크포인트 ② 에 "검증된 것이 아니라 건너뛴 것"으로 올린다. 검증과 미검증을 뭉뚱그리면 안 된다.

**drift 3라운드 상한** — 스크립트가 유예로 전환해 통과시키고 그대로 배포된다. 남은 건을 체크포인트 ② 와 커밋 메시지에 남긴다. 조용히 지나가면 안 된다.

**`merge --ff-only` 실패** — 작업하는 사이 누가 main 에 커밋한 경우다. **강제로 밀지 않는다.** ① 로 돌아가 main 을 브랜치로 다시 당기고, drift 게이트를 다시 통과시킨 뒤 재시도한다.

**pre-commit 이 커밋을 막을 때** — 정상 동작이다. 리포트를 읽고 고쳐 재시도한다. `SKIP_DRIFT=1` 이나 `--no-verify` 는 **사용자가 명시적으로 지시할 때만** 쓴다.

**글 폴더를 rename 했을 때** — 셋이 따라온다. ① 그 경로로 오는 인바운드 링크를 전부 갱신, ② 공개 URL 이 바뀌므로 체크포인트에서 먼저 승인, ③ drift 캐시에 옛 경로 항목이 고아로 남으므로 지운다(폴더가 없어 아무도 읽지 않지만, 남은 `attempts` 카운터가 나중에 유예를 앞당긴다).

**렌더 확인이 필요할 때** — SVG 좌표를 고친 경우처럼 눈으로 봐야 하면 그때만 작업 워크트리에서 `npm install` 후 **`npm run dev -- 4322`** 로 띄운다. **4321 은 쓰지 않는다.** `dev.sh` 의 프로세스 정리는 `pgrep -f "$ROOT/node_modules/.*astro"` 로 경로를 매칭하므로 원본 저장소의 서버는 죽지 않지만, 포트가 겹치면 dev.sh 가 누가 잡고 있는지 알리며 멈춘다. 끝나면 `npm run dev:stop`. `npm run build` 는 dev 서버가 뜬 채로 돌리면 콘텐츠 스토어를 동시에 써서 본문이 빈 페이지가 조용히 만들어질 수 있으므로 쓰지 않는다.

## 범위 밖

- **다른 routine 리포트** — 지금 routine 은 `bilingual-check` 하나뿐이다. 다른 종류가 생기면 별도 커맨드를 만든다. 이 커맨드에 판별 분기를 넣지 않는다.
- **서브에이전트 브리프 템플릿 파일 분리** — 에이전트마다 프롬프트가 실제로 크게 다르다(리포트 발췌·검증된 사실·모델 등급). 공통부는 열 줄 남짓이라 파일을 나눌 만큼이 아니다.
- **리포트 자체를 고치는 일** — `docs/reports/…` 는 그 시점의 기록이다. 오진이 있었더라도 사후에 수정하지 않는다.
