## 들어가며 - Branch와 WorkTree, 뭐가 다른 거지?
AI를 접하기 전에는 git에 대해서 commit, branch와 rebase, merge, fast-forward 등 git work flow에 대한 표면적인 개념만 살짝 알고 있었습니다. 하지만 캡스톤 디자인 프로젝트에서 AI로 작업을 하고, 기능개발 하는 중에 코드리뷰를 해야하는 상황이 빈번히 나왔습니다. 

한 작업 디렉터리에서 두 개의 브랜치를 동시에 열 수는 없기 때문에, 같은 원격 레포지토리를 클론한 로컬 디렉터리를 두 개 놓고, 일일이 `fetch origin` 하면서, IDE도 동시에 두 개를 띄워놓고 작업하곤 했습니다. 이 뿐만 아니라, `.env` 등 환경변수 파일도 두 작업 디렉터리에 일일이 동기화 해줘야 하는 번거로움이 존재했습니다. 

그러던 도중 work tree라는 개념을 알게 되었고, 이를 활용해 프로젝트에서 한 작업 디렉터리에서 여러 개의 브랜치를 동시에 펼쳐놓고 병렬 작업이 가능하게 되었습니다. 

이 게시글에서는 git에서 work tree가 무엇이며, 어떻게 사용하는 지에 대해 차근차근 알아가 보겠습니다. 

## 📌 용어 정의 - commit, branch
![커밋과 브랜치](./image/commit-and-branch.png)
**커밋(commit)** 은 Github에서 명사이자 동사로, 두 가지 의미를 가집니다. 
- 명사로서의 커밋: 스냅샷(snapshot)
- 동사로서의 커밋: 스냅샷을 저장하다

즉, 커밋을 커밋한다고 말할 수도 있겠죠. 프로젝트 코드의 변경 사항을 커밋(저장)하면, 변경 사항을 포함하여 해당 시점에 프로젝트 소스 코드의 커밋(스냅샷)이 생성됩니다. 이 일련의 스냅샷들은 그 순서대로 레포지토리에 영구적으로 저장되며, 추후 reset 등을 통해 특정 커밋의 내용을 수정할 수도 있습니다. 

그리고, 커밋은 부모를 가집니다. 

```text
    (A)   <---   (B)    <---    (C) 
     ↑            ↑
(B, C의 부모)   (C의 부모)
```

**브랜치(branch)** 는 특정 커밋을 가리키는 가벼운 포인터입니다. 그 이상 그 이하도 아닙니다. Github에서는 기본적으로 main 브랜치를 제공합니다. 즉 git init으로 초기화한 프로젝트에서 첫 번째 커밋을 남기면, 그 커밋에는 main이라는 이름표가 저절로 붙는 거죠. 

참고로, Git에서 브랜치라는 이름표는 **해당 브랜치의 가장 마지막 커밋(Tip)** 하나만을 가리킵니다. 과거의 커밋들에는 이름표가 직접 달려있지 않습니다. 

그렇다면 Git은 과거의 커밋들이 특정 브랜치에 속해 있다는 것을 어떻게 알까요? 바로 '꼬리 물기(Linked List)' 때문입니다. Git의 모든 커밋은 자신의 '부모 커밋(이전 커밋)'이 누구인지 기억하고 있습니다.

```text
(A) <--- (B) <--- (C) 
                   ↑
                 [main] (이름표)
```

위 그림에서 main이라는 이름표는 오직 커밋 C에만 달려 있습니다. 하지만 C가 B를 가리키고, B가 A를 가리키기 때문에, Git은 "아, A와 B도 main 브랜치에 속해 있는 히스토리구나"라고 역추적해서 파악하는 것입니다. 즉, 체인의 가장 마지막 고리 하나만 잡고 끌어올리는 것과 같은 원리입니다.

**특정 커밋에 이름표(브랜치)가 두 개 이상일 수 있나요?**

물론 특정 커밋에서 분기하면 이름표(브랜치)는 두 개 이상 달릴 수 있습니다. 예를 들어, 현재 main 브랜치의 최신 커밋 C에서 feature라는 새로운 브랜치를 만들었다고 가정해 보겠습니다. (git branch feature)

```text
(A) <--- (B) <--- (C) 
                   ↑
                [main] 
               [feature]
```               
- 새로운 커밋이 생기거나 파일이 복사되는 것이 아닙니다.
- 그저 C라는 동일한 커밋을 가리키는 새로운 포인터(이름표)만 하나 더 추가될 뿐입니다.
- 그래서 브랜치를 새로 만드는 작업이 순식간에(0.1초도 안 걸려서) 이루어지는 것입니다.

**그러면 브랜치가 분기되는 시점은 언제일까요?**
두 이름표가 같은 커밋을 가리키고 있다가, 우리가 feature 브랜치로 이동(switch)해서 새로운 커밋 D를 만들면 그때부터 비로소 길이 갈라지기 시작합니다.

```text
                        [main]
                          ↓
(A) <--- (B) <--- (C) <- (E)
                   ↖ 
                    (D)
                     ↑
                 [feature]
```
새로운 커밋 D가 추가되면, 현재 활성화된 feature 이름표는 새 커밋 D로 이동합니다. 하지만 main 이름표는 여전히 C에 남아있게 되며, 이때부터 두 브랜치의 히스토리가 분리되는 것입니다.

아까 체인의 가장 마지막 고리 하나만 잡고 부모를 타고 올라가면서 해당 커밋들이 브랜치에 속해있다고 판단한다고 했습니다. 따라서 위 그림에서 A, B, C 커밋 모두 main 브랜치에 속해있으며, 그와 동시에 feature 브랜치에도 속해있는 것입니다. 하지만 E는 feature 브랜치가 아니며, D는 main 브랜치가 아닙니다. 

Git에서 "특정 브랜치에 속해 있다"는 말의 진짜 의미는 "해당 브랜치 이름표에서 출발해 부모 커밋을 따라 거슬러 올라가면 만날 수 있다(도달 가능하다)"는 뜻입니다.

## :table: 워크트리는 뭔가요?
하나의 Git 저장소(Repository)에서 여러 개의 물리적인 작업 디렉토리(Working Directory)를 동시에 열어둘 수 있게 해주는 기능입니다.
일반적으로 하나의 작업 디렉토리에서는 한 번에 하나의 브랜치만 체크아웃할 수 있지만, Worktree를 사용하면 하나의 작업 디렉토리 하위에 또다른 작업 디렉터리를 생성하게 됩니다. 이를 통해 .git 히스토리를 공유하면서 서로 다른 폴더에서 서로 다른 브랜치를 동시에 체크아웃할 수 있게 됩니다. 마치 하나의 방에서 책상을 여러 개 펼쳐놓고 동시에 작업할 수 있게 되는 거죠. 

어떻게 하나의 레포지토리에서 동시에 여러 개의 브랜치를 띄울 수 있을까요? 그 원리를 .git 안에 들어가는 내용물에 기초해서 알아보겠습니다.

## :share: 코드 데이터는 공유, 작업 상태 데이터는 분리
하나의 레포지토리에서 여러 브랜치를 동시에 열 수 있는 원리는 Git이 **'데이터(객체)'와 '상태(HEAD, Index)'를 분리해서 관리할 수 있도록 설계**되었기 때문입니다.
보통 우리가 아는 Git 레포지토리의 .git 폴더 안에는 크게 두 가지 종류의 데이터가 있습니다.

![dot-git-inside](image/dot-git-inisde.png "w=220")

1. 공유 데이터 (모든 브랜치가 공통으로 사용):
    - objects/: 소스 코드의 스냅샷, 커밋 내역(Tree, Blob, Commit 객체) 등 실제 데이터베이스.
    - refs/: 브랜치(heads)와 태그(tags)가 어떤 커밋을 가리키는지 저장하는 포인터.

2. 작업 상태 데이터 (현재 작업 공간에 종속적):
    - HEAD: 현재 내가 작업 중인(체크아웃한) 브랜치가 무엇인지 가리키는 파일 (예: ref: refs/heads/main).
    - index: 다음 커밋을 위해 git add 해둔 변경 사항이 담긴 Staging Area.

**:branch: git switch의 작동 원리 (1 레포 = 1 브랜치)**

`git switch feature` (또는 checkout) 명령어는 동일한 디렉토리 안에서 상태만 교체하는 방식입니다.

1. .git/HEAD 파일의 내용을 ref: refs/heads/feature로 덮어씁니다.
2. .git/index를 새로운 브랜치의 상태로 초기화합니다.
3. 실제 눈에 보이는 파일들(Working Directory)을 feature 브랜치의 스냅샷으로 싹 덮어씁니다.

**한계점**: 물리적인 HEAD 파일과 index 파일이 각각 1개씩밖에 없기 때문에, 한 폴더 안에서는 한 번에 하나의 브랜치 상태만 유지할 수 있습니다.

**:worktree: git worktree의 작동 원리 (공유 데이터는 하나, 상태는 여러 개)**

`git worktree add ../hotfix-folder hotfix-branch`를 실행하면 파일 시스템 트릭을 사용합니다. 용량이 큰 objects는 복사하지 않으면서, 각 폴더가 독립된 HEAD와 index를 갖게 만듭니다.
![structure-of-worktree](image/structure-of-worktree.png)

워크트리를 만들면 .git 폴더 안에 worktrees/ 라는 새로운 디렉토리가 생기고, 그 안에 새로 만든 워크트리 전용 상태 파일들이 저장됩니다.

```text
원본프로젝트/.git/
 ├── objects/         (공유: 모든 커밋 데이터)
 ├── refs/            (공유: 모든 브랜치 포인터)
 ├── HEAD             (메인 폴더의 현재 브랜치)
 ├── index            (메인 폴더의 Staging Area)
 └── worktrees/
      └── hotfix-folder/
           ├── HEAD   (새 워크트리의 현재 브랜치)
           ├── index  (새 워크트리의 Staging Area)
           └── gitdir (새 워크트리의 물리적 경로 기록)
```
![structure-of-sub-worktree](image/structure-of-sub-worktree.png "w=220")
워크트리 하위에는 `objects/`랑 `refs/`가 없지만, `HEAD`와 `index`는 있죠? 바로 위에서 워크트리는 루트 작업 디렉터리의 .git에서 공유 데이터인 `objects/`와 `refs/`는 공유하지만, 작업 상태 데이터인 `HEAD`와 `index`는 따로 가진다고 언급한 점을 확인할 수 있습니다. 

새로 생성된 hotfix-folder 안에도 .git이 있지만, 이것은 폴더가 아니라 단순한 텍스트 파일입니다.
이 텍스트 파일을 열어보면 아래와 같이 원본 레포지토리의 경로가 적혀 있습니다.
```text
gitdir: <project-path>/.git/worktrees/hotfix-folder
```

워크트리에 있는 .git 파일이 저 내용을 가지고 있는 이유는, 해당 폴더 안에서 Git 명령어를 실행했을 때 "진짜 데이터와 현재 상태 파일들이 어디에 있는지" 알려주는 네비게이션(이정표) 역할을 하기 때문입니다.

**git status나 git commit을 쳤을 때 무슨 일이 벌어질까요?**

일반적인 레포지토리라면 .git 폴더 안에 들어가서 데이터를 읽겠지만, 워크트리에서는 .git이 단순한 텍스트 파일입니다. Git은 이 파일을 열어보고 이렇게 행동합니다.

- "아, 이 폴더는 독립된 저장소가 아니라 워크트리구나!"
- "내 진짜 HEAD(현재 브랜치)와 index(스테이징 에어리어)는 /path/to/원본프로젝트/.git/worktrees/hotfix-folder/에 있네. 거기로 가서 상태를 읽어야겠다."
- "커밋을 저장할 때는 원본 프로젝트의 objects/ 폴더를 같이 써야지."

즉, 이 한 줄짜리 텍스트 파일이 없으면 Git은 워크트리 폴더를 단순한 일반 폴더로 인식해 버리거나, 데이터를 어디서 읽어와야 할지 길을 잃게 됩니다.

**왜 심볼릭 링크(Symlink) 대신 텍스트 파일을 썼을까요?**

"그냥 원본 .git 폴더를 가리키는 바로가기(Symlink)를 만들면 안 되나?"라고 생각할 수 있습니다. 하지만 텍스트 파일(gitdir: ...)을 사용한 데에는 아주 중요한 이유가 있습니다.

- 상태의 분리: 단순히 원본 .git 전체를 바로가기로 연결해 버리면, 워크트리에서도 원본 프로젝트의 HEAD(현재 브랜치)와 index를 똑같이 공유하게 됩니다. 우리는 '커밋 데이터'는 공유하되 '작업 상태'는 분리하려고 워크트리를 만든 것이므로, 텍스트 파일을 통해 원본 .git 안에서도 워크트리 전용 서브 폴더(worktrees/hotfix-folder/)를 정확히 타겟팅해야 합니다.
- OS 호환성: 심볼릭 링크는 윈도우(Windows)와 리눅스/맥(Unix) 환경에서 처리하는 방식과 권한 설정이 다릅니다. 반면, 단순 텍스트 파일을 읽어 경로를 추적하는 방식은 모든 운영체제에서 100% 동일하고 안전하게 동작합니다.

**워크트리가 원본 프로젝트를 바라보는 것뿐만 아니라 원본 프로젝트도 워크트리의 위치를 정확히 알고 있습니다.**

원본 프로젝트의 .git/worktrees/hotfix-folder/ 안에 들어가 보면 반대로 gitdir 파일이 하나 더 있습니다. 거기에는 현재 생성된 워크트리의 물리적 폴더 경로(예: /path/to/hotfix-folder)가 적혀 있습니다.

이러한 양방향 연결 덕분에 다음과 같은 안전장치가 작동합니다.

- 사용자가 원본 폴더에서 git worktree list를 치면, 현재 어떤 폴더들에 워크트리들이 흩어져 있는지 목록을 쫙 보여줄 수 있습니다.
- 워크트리에서 사용 중인 브랜치는 원본 폴더에서 실수로 삭제(git branch -D)할 수 없도록 Git이 막아줍니다. 

```bash
raewookang@Raewooui-MacBookAir GithubBlog % git branch
  claude/bilingual-check-2026-08-03
  claude/cv-coming-soon-2026-08-03
+ claude/post-git-vs-claude-worktree
* main
raewookang@Raewooui-MacBookAir GithubBlog % git worktree list
/Users/raewookang/GithubBlog                                        db05656 [main]
/Users/raewookang/GithubBlog/.claude/worktrees/post-worktree-guide  2a985f3 [claude/post-git-vs-claude-worktree]
```
위 결과에서 확인할 수 있듯이, 루트 작업 디렉토리에서 `git branch`를 해도 워크트리 브랜치는 `+` 표시로 떠있고, `git worktree list`를 하면 워크 트리 브랜치가 무엇이고, 물리적으로 어디에 위치해 있는 지도 보입니다. 

> 💡 **흔한 오해: 커밋은 브랜치에 종속된 거 아닌가요? 커밋도 워크트리에서 따로 관리해야하지 않나요?**
>
> 아닙니다. **브랜치는 단순히 특정 커밋에 붙은 이름표일 뿐입니다.** 커밋이 브랜치에 속하는 것이 아니라, 브랜치라는 이름표가 특정 커밋에 붙어있는 것뿐입니다. 이름표를 떼어버린다(브랜치를 삭제한다)고 해서 커밋 데이터 자체가 사라지는 것은 아닙니다.
>
> **Detached HEAD 상태**: 특정 커밋의 해시값(예: git checkout a1b2c3d)으로 직접 이동해 본 적이 있으신가요? 이때 Git은 "Detached HEAD(브랜치에서 분리됨)" 상태라고 경고합니다. 이는 **어떤 브랜치(이름표)도 안 붙어 있는 야생의 커밋**을 내가 직접 보고 있다는 뜻입니다. 즉, 커밋은 브랜치 없이도 존재할 수 있습니다.

> 💡 **왜 커밋을 워크트리마다 따로 관리하지 않을까요?**
> 
> 커밋은 원래부터 브랜치에 얽매이지 않는 독립적인 데이터베이스이기 때문에, 중앙(`.git`)에 하나만 두고 여러 워크트리가 이를 공용으로 돌려쓰는 구조가 가능하고 또 효율적인 것입니다.
>
> 만약 워크트리를 만들 때마다 커밋 데이터를 각 폴더에 따로따로 분리해서 관리한다면 어떻게 될까요? 그것은 워크트리가 아니라 **그냥 레포지토리를 여러 번 새로 다운로드(Clone)하는 것과 똑같아집니다**.
> Git Worktree가 존재하는 핵심 목적은 **"가볍고 빠르게"** 여러 작업 환경을 띄우는 것입니다.
> 
> 커밋 데이터는 매우 무겁습니다.
> - `.git/objects` 폴더 안에는 소스코드의 과거부터 현재까지 모든 스냅샷(커밋)이 압축되어 들어 있습니다. 프로젝트가 크면 이 용량이 수백 MB에서 수 GB에 달합니다. 워크트리를 3개 띄운다고 이 거대한 데이터를 3번 복사하면 하드디스크 용량이 엄청나게 낭비됩니다.
> 
> `도서관과 열람실`에 비유해보겠습니다.
> - 원본 프로젝트의 `.git/objects`: 모든 책(커밋)이 모여 있는 중앙 도서관의 '지하 보존서고'입니다.
> - 각 Worktree: 책을 가져와서 읽고 글을 쓰는 '개인 열람실(책상)'입니다.
> 
> 각각의 열람실(워크트리)에 도서관의 모든 책을 복사해 둘 필요는 없습니다. 열람실에서는 "내가 지금 몇 번 책을 펴놓고 있는지(`HEAD`)", "새로 어떤 글을 쓰고 있는지(`index`)"에 대한 상태 정보만 각자 따로 관리하면 됩니다. 새로운 책(커밋)을 하나 완성하면, 그것은 다시 중앙의 보존서고(`.git/objects`)에 잘 끼워 넣어서 모든 열람실이 그 책을 공유할 수 있게 만듭니다.
